`v8.0.66-fleet.4` is built from `4a1d49c3c839d97411a6a29b5daa18e16212c3bf`, the m5-ops tip after PR #5. ## Qualification before activation

GPT-6.2 Sol built both images from a clean `git archive` of the source and ran each in an isolated loopback staging container with an empty auth directory: health 200, version header, binary commit and OCI revision, `auth-cursor` 2.1.1 with its pinned library hash, usage aggregation off with `DO_NOT_TRACK=1`, and the date-pin regression tests on the exact source. The inference gate sends four Claude Code-shaped requests in one client session through the host: a pool turn (streaming), a second pool turn (non-streaming), a named `t3-gmail` turn (streaming) and a subagent turn (streaming, `X-Claude-Code-Agent-Id`). On both hosts each returned HTTP 200, `end_turn` and the exact expected text, every request in the session carried the same injected date (2026-11-18, the Los Angeles date), and the second turn read 37,574 cached tokens. The same gate also passed on fleet.3 just before activation. The Mac baseline's first turn wrote 37,545 cached tokens, Will's baseline read that same prefix because both hosts use the same account, and each host's first fleet.4 turn read exactly those 37,545, so the switch kept the cached prefix. Only `t3-gmail` had weekly quota at the time.

After activation, `fleetctl parity` reported no configuration drift and one `P7/credential-error` on Will. It is a Codex account with a `model_not_supported` cooldown for one model, set at 03:17 PST before activation. After a restart that cooldown is the account's only model state, so the account-level summary reads unavailable, but the selector still serves the account for every other model (`sdk/cliproxy/auth/selector.go:1259-1290`). The cooldown ends at 15:17 PST.

On the affected host only: restore `.env` (and on Will the Compose file, manifest and workload contract) from the private backup under `ops/runtime/fleet4-activation-20261118/`, then run the same `docker compose up` command and both verifiers. Config and OAuth files are not part of the rollback.

## As-run scripts

These are as-run records, not maintained tools. Their paths and hosts are those of 2026-11-18. They are byte-identical copies of the private runtime files on the Mac: the first two are from `ops/runtime/fleet4-20261118/`, and `inference_gate.py` is from `ops/runtime/fleet4-activation-20261118/`. The build reports, logs, receipts and backups they wrote stay private. The exported source tree's `docker-build.sh` is not copied: it is byte-identical to the repository's own `docker-build.sh` at `4a1d49c3`, and neither script calls it. Check a copy with `shasum -a 256 <file>`.

- `build_images.py` (sha256 `23688963c45211b922c3020184489dd9ee1dea6e9ae703d0c1e7d1be1dbe6cf5`): run as `build_images.py <arch> <builder-image> <source-sha256> <build-date>`, once per architecture. The arm64 path uses Mac paths and a 15 GiB free-disk floor, and the amd64 path uses Will paths and a 150 GB floor. The script first checks four things: the free disk, that the release tag does not exist yet, that `source.tar` has the given sha256 and archive commit `4a1d49c3`, and that the exported `source/` tree matches the archive file by file. Then it compiles the server with Go 1.26.10 in a `--network none` builder container with `GOPROXY=off`. It builds `cliproxy-fleet:v8.0.66-fleet.4` from the manifest's parent image with OCI revision and version labels, and it runs the date-pin tests (`TestClaudeCloakedDateReminder`, `TestClaudeDatePinSessionID`) with `go test -json`. It prints one `<arch>: <step>` line per step and writes details to `<arch>-build.json` and per-step logs.
- `qualify_staging.py` (sha256 `d31a1d58c3a02bd5c14fce5ab6ca970a4ee688b72eb4ec8151d34aa80b4c2177`): run as `qualify_staging.py --arch <arch>` after the build. It starts the built image as `cliproxy-fleet4-<arch>-stage` with `--network none`, a synthetic loopback config (quota-aware routing, session affinity off, `auth-cursor` enabled, usage statistics off), an empty tmpfs auth directory, and the pinned Cursor plugin library mounted read-only. Its management password is a fixed public probe value that is valid only inside that container. It checks loopback health, the version header, binary commit and OCI revision, image ID and binary hash, plugin registration and library hash, `DO_NOT_TRACK=1` and `GOTELEMETRY=off`, no credentials, no published ports or writable bind mounts, and the removal of the container. It prints `<arch> staging: passed` or the names of the failed checks, exits non-zero on failure, and writes details to `<arch>-qualification.json` and `<arch>-startup.log`.
- `inference_gate.py` (sha256 `e693ddb095251e633fbe6785d81849775f6379b455dbdc5f158d9ff6bf6aee6c`): run as `inference_gate.py <base-url> <label> [<log-dir> | ssh:<host>]`. It reads the client key from `~/.local/bin/cliproxy-codex-token`. Then it sends the four `claude-haiku-5-5` requests described above, all in one random `X-Claude-Code-Session-Id` with a Claude Code user agent. Its output is a series of JSON lines. One line per request gives the status, stop reason, cache read and write tokens, seconds, and whether the text matched. On an HTTP error that line holds the status and up to the first 300 characters of the error body instead. The reply text and the key are never printed. The injected-date check runs only when a log argument is given. Then one line gives the injected date of each logged request, read from the host's request logs, and the gate also requires at least four logged requests with one date. The `ssh:` form reads `/home/andrew/cliproxy/logs` on the host with `sudo -n`. Without a log argument the gate can pass with no date check. One line covers the turn 2 cache read. A final `{"gate": <label>, "passed": ...}` line gives the result. A connection error, a timeout or a key command failure instead ends the script with a Python traceback and no gate line. The script exits 0 only if every check passed. The file was last modified at 10:00:03 PST, before the Mac activation at 10:00:32. This record does not show whether the fleet.3 baseline runs used these same bytes.
