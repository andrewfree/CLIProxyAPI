# Docker watchdog false restart remediation

Status: implemented and verified; all 40 focused operations tests and the
final natural scheduled run pass. The live Docker engine and containers
remained running throughout validation. No Docker or container restart was
part of this change.

## Cause

The watchdog used a single `docker info` invocation with a ten-second deadline
as the trigger for a forced Docker Desktop restart. On September 7, the
Desktop API continued answering pings and container listings during three
failed watchdog checks. The CLI did not send an `/info` request in those
windows. Host CPU and memory pressure made a CLI startup delay plausible,
but the old watchdog did not retain enough diagnostics to identify that
delay precisely.

The log recorded five forced-restart attempts between 00:20 and 00:58 PDT,
eleven on September 6, and 84 since August 27. More restarts occurred before
remediation began. The baseline captured at 01:18 PDT had Docker backend PID
22848, started at 01:16:24, and `staging-track`, `cli-proxy-api`, and `slk`
started at `2026-09-07T08:16:29Z`.

## Change

- Probe the configured local Docker socket directly without the Docker CLI
  or plugin startup. Reject remote endpoints for this local recovery job.
- Require three consecutive failures of both the socket ping and proxy
  health, clear stale failures, and recheck availability before global
  recovery. Either service responding suppresses a Desktop restart.
- Increase the default Desktop restart cooldown from five to thirty minutes.
- Keep scoped proxy repair. CLI execution failures do not count as DNS
  failures or contribute to the separate consecutive DNS failure counter.
  Persistent DNS failure cannot escalate to a global restart while the
  engine and proxy are responsive.
- Make `--check-only` leave recovery state unchanged. Record bounded socket
  diagnostics and successful check completion without request or auth data.

## Resolver exit-status contract

The live container's `/usr/bin/getent --version` identifies Debian GLIBC
`2.36-9+deb12u14`; its `--help` confirms that `ahostsv4` is supported. The
repository Dockerfile also uses `debian:bookworm`.

[Debian Bookworm's getent(1) documentation](https://manpages.debian.org/bookworm/manpages/getent.1.en.html)
defines exit status 1 as missing arguments or an unknown database, status 2
as a supplied key not found, and status 3 as unsupported enumeration. The
watchdog invokes `getent ahostsv4 HOST`, so only status 2 counts as a failed
lookup. Status 1 and Docker CLI execution failures remain probe errors.
This was verified from the installed binary's metadata and the manual;
no DNS or network failure was induced.

## Remaining limits

The host still needs enough CPU, memory, and disk headroom. This change fixes
the watchdog's false-restart policy; it is not evidence that every possible
Docker or macOS crash has been eliminated. A confirmed engine-and-service
outage now waits for three scheduled observations, normally about four to
six minutes, and the restart cooldown can defer repeated recovery attempts.
Persistent DNS failure with a responsive engine is logged for investigation.
